ROTS architecture

Lives in bevy2025/docs/architecture.html. Change it in the same PR as any change to a flow, wire contract or state machine on this page.

Every ROTS service is stateless. Fleet state — which game servers are alive, whose character is on which slot — lives in one Temporal coordinator workflow; per-login state lives in a Temporal session workflow; accounts and characters live in Postgres (rots-db). Any authserver replica can answer any request, and a rolling deploy costs nothing but a moment of /play.

Overview

Three processes and one database:

Authserver

Accounts, sessions, game tickets, and the Temporal worker for both workflows. Serves the public API behind /auth and an internal API for game servers. Owns no state of its own.

Game server

Authoritative simulation for one slot. Verifies tickets offline, asks to be admitted, then reports its roster every 10 s. Never talks to Temporal.

Client

Native (UDP) or web (WebSocket). Presses Play now, gets a ticket plus a server, connects.

Two Temporal workflows carry the state that used to be nowhere:

Coordinator rots-coordinator-<queue>

One per environment. Owns the fleet: which slots exist, their boot ids and rosters, and the reservations it handed out. State machine.

Session rots-session-<queue>-<sid>

One per login. Tracks whether the session is in menus, assigned to a slot, or in game. State machine.

Play: from button to in game

  1. POST /auth/api/v1/play with the session (bearer token or cookie). No session → 401 no_session.
  2. The authserver sends an update-with-start play to the session workflow rots-session-<queue>-<sid>, creating it on first use. The update carries the session row's current character_id and account_id: the workflow never stores a character, so a later "play" after switching characters is placed independently.
  3. A local activity (assign_server, ≤3 s) sends an update-with-start assign to the coordinator with the character id, sid and the session's preferred slot.
  4. The coordinator picks: a slot the character is already on, else the preferred slot if healthy, else the least loaded (players + reservations), ties to the lowest slot. It reserves the slot for 360 s (ticket TTL 300 s + 60 s leeway).
  5. A local activity (mint_ticket, ≤4 s) reads the character row and signs an EdDSA ticket whose srv claim is the assigned slot. Its sid claim is the login session id.
  6. The authserver answers 200 {"ticket","expires_at","character_id","kind","server":{"slot","udp","ws_path"}}; the client stores the ticket and the assigned server.
  7. The client connects to server.udp (native) or server.ws_path on the page's own host (web), presenting the ticket in its ConnectRequest.
  8. The game server verifies the ticket offline against the authserver's public key (fetched once at boot), and refuses it if srv is not its own ROTS_SERVER_SLOT.
  9. The server asks the coordinator to admit the character — Figure 3. Only then does the player enter the world.

Time budget. One /play costs at most 3 s of assigning plus 4 s of minting, for a 10 s HTTP timeout. The playing flag in the session workflow keeps two plays from interleaving inside one workflow task.

Presence: joins, leaves, heartbeats

  1. vet_connect_requests verifies the ticket, drops resends from a connection it already accepted, and rejects a second connection for a character that is connected, joining or waiting. With a coordinator configured it queues a join; otherwise (testing gym, standalone server) the request is admitted immediately.
  2. The join goes out through the server's single FIFO sender with the ticket's sid, and waits up to 6 s.
  3. The authserver first checks that the sid is still a live session. Logging out, a newer login or a claim deletes the row, so a stale ticket cannot join.
  4. It sends the coordinator an Update join. The coordinator admits a character it does not already hold on another healthy slot.
  5. The coordinator queues presence{slot, character_id, present:true} for that session's workflow and signals it when the run loop next drains the outbox — after the join update has already answered, so the session may still read assigned for a moment while the player is admitted.
  6. The answer decides the client: 200 admitted → admit_players spawns the player; 409 session_ended → ConnectRejected "session ended"; 409 already_on_other_server → "character already connected on another server"; any other failure or no answer in 6 s → "coordinator unavailable".
  7. While the player is connected the server reports its roster every 10 s, and reports a leave when the player disconnects (quit, timeout). Both are retried with 1-2-4 s backoff, then every 4 s until accepted; a 400 is logged and dropped (retrying cannot fix a malformed body). The coordinator diffs rosters to notice players that vanished, and signals presence{... present:false}.

The FIFO sender is load-bearing. The coordinator learns that a player left by comparing a heartbeat's roster with the slot's recorded players, and it never re-adds players from a heartbeat of a known boot id. A heartbeat that overtook a join would therefore drop the player who had just joined, permanently. One task sends every op, one at a time, in production order — and the server's roster includes players whose join is still in flight for the same reason.

Logins are checked at join only. A player already in game is not removed when their login ends: no kick, no ticket renewal. Their session workflow ends at logout; the disconnect the server still reports has no session left to update, and any further connect with the old ticket is rejected as session ended. Presence is a lease, not a fence: a game server cut off from the authserver keeps simulating, and the coordinator forgets its players after COORDINATOR_STALE_SECS, so the same character can be admitted elsewhere in that window. Character state is not persisted yet; once it is, that write needs an epoch issued by the coordinator.

Runs and restarts. The coordinator continues as new when Temporal suggests it, after 2000 events, or after an hour — and only when handlers are done and the outbox is empty; the carried fleet state is passed as the new run's input. A 1 h timer in the run loop is what makes that happen: a loop that only waits for the outbox would never wake while the fleet is idle. The 3 h run timeout only closes a coordinator that could not continue as new (a deleted preview); the next with-start call recreates it, and it rebuilds by adopting each slot's first heartbeat roster.

Determinism. Workflow code uses BTreeMap/BTreeSet only, takes time from ctx.workflow_time(), does no I/O and no randomness (activities do that), and wraps any change to the command sequence — new activities, timers, signals, continue-as-new — in ctx.patched("<change-id>"), because old and new authserver pods poll the same queue during a rolling deploy.

Ceiling. One workflow serializes every fleet event: roughly 1 event/s comfortably, a few tens/s before a run hits its cap (2000 history events or 1 h, whichever comes first). Production's four servers produce about 0.4 events/s. Past ~100 reporting servers, shard the coordinator by slot range or move presence out of Temporal.

Presence is keyed by (slot, character), not by slot. One login may hold two characters on the same server (a later feature); one leaving must not report the other as gone. The workflow stores no character: every play carries the session row's current character_id. The run ends after logout — even with a player still connected: they keep playing, and the coordinator's later present:false finds a closed workflow and drops it — or after 24 h once nobody is present. Either way it first waits for an in-flight play to answer. Its execution timeout is 48 h, so a deleted preview closes its sessions too.

The web client needs the gateway's same-origin /auth, so test it on a preview.
