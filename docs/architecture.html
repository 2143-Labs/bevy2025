ROTS architecture

Lives in bevy2025/docs/architecture.html. Change it in the same PR as any change to a flow, wire contract or state machine on this page.

Every ROTS process is stateless. Fleet state — the directory of game-server instances, and which character is on which instance — lives in one Temporal coordinator workflow. Each game-server instance has its own Temporal instance workflow, which holds that instance's lease and roster and owns its lifecycle. Per-login state lives in a session workflow; accounts and characters live in Postgres (rots-db). Any authserver replica can answer any request, and a rolling deploy costs nothing but a moment of /play.

Overview

Three processes and one database:

Authserver

Accounts, sessions, game tickets, and the Temporal worker for all three workflows. Serves the public API behind /auth and an internal API for game servers. Owns no state of its own. In managed mode it is also the only process that creates and deletes the game-server instances, through the Kubernetes API.

Game server

Authoritative simulation for one slot. Verifies tickets offline, asks to be admitted, then reports its roster and connected count to its own instance workflow every 10 s. Never talks to Temporal directly — the authserver's internal API is its only path.

Client

Native (UDP) or web (WebSocket). Presses Play now, gets a ticket plus a server, connects.

Three Temporal workflows carry the state that used to be nowhere:

Coordinator rots-coordinator-<queue>

One per environment. Owns the directory — per slot: the generation, the phase, the join code and the UDP port — the character index (character → instance), the reservations it hands out, and the decision to place a character on an existing instance or spawn a new one. It receives no heartbeats; instances report lifecycle changes to it as signals. State machine.

Instance rots-gs-<queue>-<k>-g<g>

One per game-server instance. Owns the instance's lease, its roster and its lifecycle: provision the pod, wait for the first heartbeat, serve, drain, delete. Reports server_ready, server_status, release and server_gone to the coordinator, and presence to sessions. State machine.

Session rots-session-<queue>-<sid>

One per login. Tracks whether the session is in menus, assigned to a slot, or in game. State machine.

Play: from button to in game

  1. POST /auth/api/v1/play with the session (bearer token or cookie). No session → 401 no_session.
  2. The authserver sends an update-with-start play to the session workflow rots-session-<queue>-<sid>, creating it on first use. The update carries the session row's current character_id and account_id: the workflow never stores a character, so a later "play" after switching characters is placed independently.
  3. A local activity (place_character, ≤3 s) runs the coordinator's place update with the character id, sid and a location (always None today: no character has a saved position, so the field is the extension point for world-aware placement).
  4. Placement is pure and first match wins: the instance the character is indexed on; else an unexpired reservation; else, in managed mode, the lowest free slot with the next generation and a fresh join code — the slot becomes Provisioning, the character is reserved for 360 s (or the ready timeout plus 360 s) and a spawn effect is queued. Static mode picks the ready server with the fewest players and reservations below GAME_SERVER_CAPACITY_PER_SERVER, ties to the lowest slot.
  5. The coordinator drains its outbox: a local activity starts rots-gs-<queue>-<k>-g<g> (conflict policy Fail: the ids are unique per instance, so an existing workflow means the spawn already happened). The instance workflow provisions a PVC, a headless Service and a one-replica StatefulSet from the rots-gameserver PodTemplate, then waits for the first heartbeat.
  6. Starting is answered 503 server_starting and the client retries every 2 s for up to 120 s; ServersFull is 503 servers_full (every 5 s, up to 10 min) and a spawn-paused coordinator 503 no_game_server — a spawn is never waited for inside the request. Ready — an instance that is already serving, or the retry after the first heartbeat — is answered 200 {"ticket","expires_at","character_id","kind","server":{"slot","udp","ws_path","join_code","paused"}}. A local activity (mint_ticket, ≤4 s) signs the EdDSA ticket: srv is the slot, sid is the login session.
  7. The pod's first heartbeat names its (slot, generation). The instance workflow moves to Ready and signals server_ready to the coordinator (signal-with-start, so a terminated coordinator is recreated rather than lost), which fills in the UDP port, join code and player list.
  8. The client's next retry is answered with the ticket. The reservation is refreshed for the ticket lifetime, so a second /play in the same session cannot be sent to a different instance.
  9. The client connects to server.udp (native) or server.ws_path on the page's own host (web), presenting the ticket in its ConnectRequest. The game server verifies the ticket offline against the authserver's public key (fetched once at boot) and refuses it if srv is not its own ROTS_SERVER_SLOT. It then asks to admit the character — Figure 3. Only then does the player enter the world.

Time budget. One /play costs at most 3 s of placing plus 4 s of minting, well inside the 30 s HTTP timeout — which also covers KEDA's interceptor holding the first request while a scaled-to-zero authserver cold-starts. A spawn is never waited for inside the request. The playing flag in the session workflow keeps two plays from interleaving inside one workflow task.

Presence: joins, leaves, heartbeats

  1. vet_connect_requests verifies the ticket, drops resends from a connection it already accepted, and rejects a second connection for a character that is connected, joining or waiting. With a coordinator configured it queues a join; otherwise (testing gym, standalone server) the request is admitted immediately.
  2. The join goes out through the server's single FIFO sender with the ticket's sid, its slot and generation (from ROTS_SERVER_SLOT / ROTS_SERVER_GENERATION), and waits up to 6 s.
  3. The authserver rejects a slot at or above GAME_SERVER_SLOTS (400 bad_slot) and checks that the sid is still a live session. Logging out, a newer login or a claim deletes the row, so a stale ticket cannot join.
  4. It routes the report by (slot, generation) to that instance's workflow and runs the join update there. In static mode the update starts the workflow if it is not running; a managed instance's report never does, and answers 409 unknown_instance instead.
  5. The instance workflow's local activity claim_character runs the coordinator's claim update, which admits a character unless it is bound to another live instance. A Draining instance refuses every join.
  6. The instance records the character and queues presence{slot, character_id, present:true} for that session's workflow, signalling it when the run loop next drains the outbox — after the join update has already answered, so the session may still read assigned for a moment while the player is admitted.
  7. The answer decides the client: 200 admitted → admit_players spawns the player; 409 session_ended → ConnectRejected "session ended"; 409 already_on_other_server → "character already connected on another server"; 409 server_draining → the instance is shutting down and takes no new players; 409 unknown_instance → the workflow for that (slot, generation) is gone; any other failure or no answer in 6 s → "coordinator unavailable".
  8. Every 10 s the server reports its roster — every character with units in the world, connected or a ghost left by a disconnect — plus boot_id, the connected count (live connections only) and its UDP port. A disconnect sends nothing; the character is released (POST /internal/v1/servers/leave) only when its camera unit is despawned, which is its death. Reports are retried with 1-2-4 s backoff, then every 4 s until accepted; a 400 is logged and dropped (retrying cannot fix a malformed body). A heartbeat in managed mode that gets 409 unknown_instance means the instance does not exist any more: the server writes its shutdown sentinel and exits 0.
  9. The instance workflow diffs rosters: the first heartbeat of a boot id adopts the roster it sees — that is how a workflow that lost its state recovers, and how a world restored from its statefile re-adopts its ghosts — and later heartbeats of the same boot only remove players, so a refused join that appears in a roster cannot resurrect a character. A removed player gets presence{... present:false} and the coordinator gets release. Two stale windows (2 × COORDINATOR_STALE_SECS) without a heartbeat end the workflow: presence false for everyone, server_gone{Lost} for the coordinator, and in managed mode the StatefulSet and PVC are deleted.
  10. The server also decides when it is finished: it posts POST /internal/v1/servers/shutdown-request {slot, generation, boot_id, reason, players} (reason idle when nobody has been connected for ROTS_IDLE_SECS, with ghosts not counted, or sigterm when the kubelet stops the pod and the instance keeps no statefile), the instance workflow's shutdown update asks the coordinator's request_shutdown, and the answer is a plan: {"plan":"destroy"} (nobody to move — exit, the instance is deleted) or {"plan":"to_menu"} (send every client HostMigration::ToMenu, wait for them to leave, then exit). A granted shutdown marks the slot Draining and unbinds its characters immediately. An instance that does keep a statefile (ROTS_STATE_DIR) handles SIGTERM differently: it pauses the world, writes the final snapshot, and exits 0 without the sentinel and without a shutdown request, so the StatefulSet restarts the pod on the same volume and the world comes back paused (PauseReason::Restoring) until its players return or 30 s pass. Idle counting is skipped while the world is paused for either reason, because both mean nobody should be connected: Restoring (its players have not reconnected yet) and PreGame (a warm-pool instance that has never been online). A pre-game instance therefore reports, answers /healthz and keeps its coordinator link up while it waits for POST /activate, and its idle clock starts on the activation frame.

The FIFO sender is load-bearing. The instance workflow learns that a player left by comparing a heartbeat's roster with its recorded roster, and it only takes players from the first heartbeat of a boot id — which is also what lets a workflow that lost its state rebuild. A heartbeat that overtook a join would therefore drop the player who had just joined, permanently. One task sends every op, one at a time, in production order — and the server's roster includes players whose join is still in flight for the same reason. Ghosts are the third group: a character whose player disconnected keeps its units, so it stays in the roster until it dies. Two Bevy orderings keep the roster honest: the timed heartbeat runs after admit_players (so a player admitted this frame is already a ConnectedPlayer), and report_leaves runs after both disconnect writers and before the heartbeat.

Logins are checked at join only. A player already in game is not removed when their login ends: no kick, no ticket renewal. Their session workflow ends at logout; the presence the instance workflow still sends has no session left to update, and any further connect with the old ticket is rejected as session ended. Presence is a lease, not a fence: a game server cut off from the authserver keeps simulating, but once two stale windows pass without a heartbeat its instance workflow declares it gone and unbinds its players, so the same character can be admitted elsewhere in that window. Character state is persisted as of slice B: the world (units with their NetEntIds, ghosts and the tick) is written to state.bin every 5 s and on SIGTERM, and restored by the restarted process. The file sits on that instance's own PVC (data-rots-gs-<k>-g<g>-0), so a world can only come back inside the instance that wrote it, and a new generation always starts with an empty volume.

Coordinator and instance state machines

The coordinator keeps two maps and nothing else about liveness. It knows, per slot, which instance owns it — the generation, the phase, the join code and the UDP port — and, per character, which instance holds it. Heartbeats never reach it: each instance's own workflow keeps the lease. The full instance lifecycle (including the recovery path) is drawn at design.html#gameserver-workflow; this figure is the part the coordinator participates in.

A fresh coordinator rebuilds from the running instances. A run that starts without carried state — the first start, or after someone terminated the workflow — first runs the local activity rebuild_directory: list_workflows for GameServerWorkflow on this task queue, the server query on each, and a merge into the directory (phases, join codes, UDP ports, rosters, and next_generation = max(generation) + 1). Each server query has 1.5 s, and an instance that does not answer (it may be waiting on the coordinator being rebuilt) is listed as Ready with an empty roster. The activity's result is in history, so replay is unaffected, and place/claim wait for it, so a /play that races the start is answered after the rebuild instead of spawning a duplicate instance.

Runs and restarts. Both workflows wake on the earliest deadline they hold or as soon as something is queued to send, and the timer that loses the select! is cancelled — Temporal SDK 1.1.1 timer futures have no Drop, so an abandoned timer would keep running. On every wake, not only when a timer fires, the loop evaluates continue-as-new: Temporal suggests it, history passed 2000 events, or the run deadline (1 h for the coordinator, 1 h per instance) is reached. The coordinator carries the fleet state into the new run; an instance carries its lease, roster and phase. The 3 h / 24 h run timeouts only close workflows that could not continue as new (a deleted preview); the next with-start call recreates the coordinator, and it rebuilds.

Determinism. Workflow code uses BTreeMap/BTreeSet only, takes time from ctx.workflow_time(), does no I/O and no randomness (activities do that), and wraps any change to the command sequence — new activities, timers, signals, continue-as-new — in ctx.patched("<change-id>"), because old and new authserver pods poll the same queue during a rolling deploy. Join codes come from a seed the coordinator carries and a splitmix step, so they are replay-safe.

Ceiling. The coordinator's history now grows with placements and lifecycle events instead of heartbeats, so one run lasts its full hour under any load: roughly 1 event/s comfortably, a few tens/s before it hits its cap. Each instance workflow takes about 360 heartbeats/h × 4 events ≈ 1,800 events/h and continues as new hourly; short-lived tutorials usually finish before their first continue-as-new. Temporal 1.32.0 carries a few hundred live instances at this shape. Beyond that, liveness has to leave Temporal — that is the ceiling this design records.

Presence is keyed by (slot, character), not by slot. One login may hold two characters on the same server (a later feature); one leaving must not report the other as gone. The workflow stores no character: every play carries the session row's current character_id. The run ends after logout — even with a player still connected: they keep playing, and the instance workflow's later present:false finds a closed workflow and drops it — or after 24 h once nobody is present. Either way it first waits for an in-flight play to answer. Its execution timeout is 48 h in prod and 2 h in previews (SESSION_EXECUTION_TIMEOUT_SECS), so a deleted preview closes its sessions too.

Postgres (55432), Temporal (17233, UI 18233), authserver (8000 public, 8001 internal), game server (25555), clientyes: the coordinator and one instance workflow, both local

The full stack's Temporal UI is http://localhost:18233; temporal workflow query -n rots --address 127.0.0.1:17233 -w rots-coordinator-rots-dev --type fleet shows what the coordinator believes (directory, index, reservations), and -w rots-gs-rots-dev-0-g1 --type server shows the instance's lease and roster. To exercise the managed path locally set GAME_SERVER_PROVISIONER=fake on the authserver: spawns and deletes are recorded instead of calling the Kubernetes API. A second local game server needs GAME_SERVER_SLOTS=2 on the stack and ROTS_SERVER_SLOT=1 ROTS_PORT=25556 on the server — 25556 is also the first server's axum port (port + 1), so the second server's axum and WebSocket listeners fail to bind and only its native UDP play works. The web client needs the gateway's same-origin /auth, so test it on a preview.
