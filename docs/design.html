1. Game overview

ROTS is a Bevy 0.20 multiplayer game with a native client (Steam) and a web/WASM client. Players log in with Steam, Discord or au.2143.me, or play as a guest. This page is its living design doc: it starts with how the systems connect, and gameplay and systems sections get added here over time.

Every new player starts in their own tutorial instance, the default map for now, with a join code they can share. An instance is a one-replica StatefulSet created at runtime by the authserver and owned by its own Temporal workflow, and each server decides when it shuts down: with nobody connected it asks the coordinator what to do with its players, destroys its world and its volume, and the workflow deletes what is left. Fleet capacity is a Kubernetes ResourceQuota; a full fleet answers 503 servers_full, so the client waits instead of failing. prod still runs the four static rots-gameserver-0..3 servers until the managed switch (#122). The full design, including placement, provisioning and the event budget, is in docs/game-server-scaling.md.

A disconnect does not take a character out of the world — on a managed instance. It keeps its state on a volume, so its world outlives a disconnect and a restart; prod's static servers have nothing to restore from, so there a disconnect still removes the character's units and reports it to the coordinator, exactly as before. The connection ends, the player entity becomes a ghost and everything they were driving stays exactly where it was — other players can still attack and kill it, and that death is real. Reconnecting rebinds the ghost: the same character, the same body, the same camera. When a server process dies its StatefulSet restarts it on the same volume and the world is restored from the statefile the server writes every 5 s. A restored world stays paused until its players are back, or for 30 s, whichever comes first; after that an absent character is live and killable like any other.

3. Enter the game

  1. The client calls POST /auth/api/v1/play with its session cookie or token.
  2. The authserver sends the update play to that login's session workflow (10 s bound).
  3. The session asks the coordinator to place the character by its id, sid and (once a character has a saved position) its location. It is always None today.
  4. With no instance for that character, the coordinator allocates the lowest free slot, the next generation and a join code, marks the slot Provisioning, reserves the character for 360 s and queues the spawn.
  5. A local activity starts rots-gs-<queue>-<k>-g<g>, which provisions a PVC, a headless Service and a one-replica StatefulSet.
  6. The client is answered 503 server_starting and retries every 2 s for up to 120 s. A full fleet answers 503 servers_full instead, retried every 5 s for up to 10 min.
  7. The new pod's first heartbeat names <k, g>; the workflow reports server_ready and the coordinator's slot becomes Ready.
  8. The next retry gets a ticket: {ticket, expires_at, character_id, server:{slot, udp, ws_path, join_code, paused}}.
  9. The client connects to that slot. The game server verifies the ticket offline with the public key and checks srv, then claims the character at the coordinator through join and is admitted or refused (already_on_other_server).
  10. A character that already has an instance skips 4–8: place answers Ready straight from the character index or an unexpired reservation.

Coming back after a disconnect

Ten seconds without a server heartbeat is a disconnect: the client does not quit, because the character is still in the world. It reconnects instead, in this order:

  1. POST /api/v1/play once for a fresh ticket — the old one may have expired, and game servers check exp. The client keeps resending ConnectRequest with the new ticket to the address it was on, once a second for up to 10 s.
  2. Still not connected: POST /api/v1/my-server-crashed (always 202) tells the coordinator to probe that character's instance.
  3. /play is polled every 2 s for up to 120 s; 503 server_recovering and 503 server_starting keep the client waiting, and a 200 carries the ticket and address to connect with.
  4. Nothing worked after that: the client returns to the main menu with "Lost connection to the server".

The player sees "Reconnecting…" throughout, on native (UDP) and on web (WebSocket) alike.

Joining another tutorial by its code

Every managed instance has a 4-character join code, shown to its players as join code: XXXX at the top right of the world. Escape opens the pause menu, which carries a join someone: ____ box under the code; typing another tutorial's code moves the character there.

  1. The client posts POST /auth/api/v1/join-code {"code"} with its session cookie or token.
  2. The authserver runs the coordinator's resolve_code update (10 s bound). Only a Ready, non-warm instance with that code can be joined. The coordinator rebinds the character's index entry to it and signals evict to the instance the character was on.
  3. That instance's workflow runs the evict_character activity, which POSTs /evict {character_id} on the server: it despawns the character's units and player entity, tells the other clients with DespawnUnit2 + PlayerDisconnected, and reports the leave to its workflow, which drops it from the roster. The moving client is sent nothing (it is already leaving, and a despawn of its own camera unit would take its camera).
  4. The client's answer is {"moved":true,"slot"}; it enters the reconnect path above (MoveToTutorial → NetworkGameState::Reconnecting), so /play now answers with the new instance and the player arrives in it as a new arrival — a fresh man, since the old world took its units.
  5. Errors: 404 unknown_join_code (no live instance has it), 409 target_unavailable (starting, recovering or draining) and {"moved":false} when the character is already there.

5. Failure behaviour

EventWhat players seeRecovery
Temporal down/play returns 503 temporal_unavailable; new joins are refused. Players already in a game keep playing.The worker reconnects every 10 s; workflow state is intact in temporal-db.
Authserver restart or outageBrief errors on login, Play and new joins; players already in a game keep playing, and a client that stops receiving heartbeats shows "Reconnecting…".None needed: the authserver keeps no state. An instance's lease may lapse, but a lapse only signals probe, and nothing is killed unless the probe says the pod is dead — so an outage longer than the lease (30 s) deletes no instance, and its world stays on its volume. A static server's workflow is recreated by its next heartbeat. An authserver that scaled to zero cold-starts behind KEDA's interceptor instead: the request waits for the pod rather than failing, and the native client allows 30 s for it.
Game server crash, hang or hard killIts players see "Reconnecting…" and come back into the same world, in the same body, where they left it.The lease lapses after 30 s (or a client's crash report arrives first) and the instance workflow probes the pod: it fetches the pod IP and asks GET /healthz with a 2 s timeout. A 200 means the server is alive — nothing is killed and the lease is re-armed. No answer means the pod is hard-killed (gracePeriodSeconds: 0), the StatefulSet restarts it on the same PVC, the process loads state.bin and the world comes back paused until its players return or 30 s pass (figure 6). A second kill within KILL_BACKOFF (300 s) is refused. No heartbeat within the 120 s ready timeout → the instance is deleted as Lost and the coordinator unbinds its characters. A pool instance in pre-game answers /healthz like any other, so it is never probed dead.
Node lostPlayers on that node see "Reconnecting…"; their characters stay in the world.The volume has two replicas (StorageClass longhorn-rots-gs), so it survives the loss of the node its pod ran on. Longhorn's nodeDownPodDeletionPolicy force-deletes the StatefulSet pod so its ReadWriteOnce volume can attach elsewhere; the pod restarts on another node with the same PVC and restores from the statefile like any other restart. If no node can run it within the ready timeout, the instance is Lost.
Fleet full503 servers_full; the client shows "Servers are full, retrying…" and retries every 5 s for up to 10 min.The ResourceQuota frees a slot when a server drains; the next Play takes it. The coordinator also holds the fleet full for 30 s after an Unschedulable pod.

6. How this doc stays current

  • Any PR that changes a flow, port, service or state rule updates this page in the same PR. A design change made here first is implemented in code in the same PR.
  • The reviewer checks the page on the PR preview at https://rots-<PR>.john2143.com/design.html.
  • Dashed arrows become solid when their PR lands.
  • CI runs scripts/check-design-doc.py: every in-page link must resolve, and the page must stay script-free.
